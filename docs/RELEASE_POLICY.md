# Release policy

Every merge into `main` starts exactly one new Android release. The release
automation — not an agent and not a human editing files — decides how far the
version advances. It deliberately advances **slowly**: a release is produced for
every merge, but the version number almost always moves by only one patch.

## Who owns what

| Concern | Owner |
| --- | --- |
| Version number and tag | `scripts/release_plan.py` (the automation) |
| Changelog | Generated by the automation, written **only** into that version's GitHub Release notes |
| APKs / AAB / checksums / `latest` | `.github/workflows/release.yml` |
| Rules for every agent | [`AGENTS.md`](../AGENTS.md) |

Agents must not bump versions, create tags/releases by hand, or write changelog
text anywhere except the GitHub Release of the version it belongs to.

## How the version step is decided

The planner looks at the published, stable releases that are ancestors of the
commit being released, takes the highest one as the baseline, and inspects the
first-parent commits since it (merge commits included). It then chooses the
smallest step the evidence justifies:

| Step | When the automation chooses it |
| --- | --- |
| **patch** (`v2.1.6 → v2.1.7`) | Default for every merge — fixes, chores, small features, one-off changes. |
| **minor** (`v2.1.6 → v2.2.0`) | At least 3 feature signals in the merged commit subjects **and** real change volume (≥150 changed lines or ≥8 files) **and** a cool-down since the last non-patch step: ≥5 published patch releases or ≥14 days. |
| **major** (`v2.1.6 → v3.0.0`) | An explicit `BREAKING CHANGE:` / `feat(api)!:` declaration **and** a longer cool-down since the last major (≥10 releases or ≥30 days). If the cool-down is not met, the automation holds at minor instead of racing ahead. |

`Release-Minor: yes` and `Release-Major: yes` on their own line in a
first-parent commit message remain deliberate, opt-in maintainer overrides. They
are not needed for normal work and must not be used to speed versions up.

Slow progression is structural, not just a preference: no single merge can skip
straight to a major without a declared breaking change, and a run of feature
work cannot produce repeated minors because each non-patch step resets the
cool-down. The chosen step and its reason are printed to the workflow job
summary (`🧭 Version decision`) and to `GITHUB_OUTPUT` as `bump`.

## Changelog contract (all agents)

`release_plan.py` writes `## ✨ Changes in <tag>` followed by one `- 📝 <commit
subject>` line per first-parent commit since the preceding published stable
release. Before anything is published, `scripts/check_release_notes.py` fails
the workflow if the notes:

- are not an emoji heading naming this version,
- contain a line without an emoji bullet,
- contain an entry that is not a commit in this version's range (including a
  copied older changelog), or
- omit any commit in this version's range.

The validated notes are passed to `gh release create --notes-file ...`, so the
changelog lives only in that version's own GitHub Release.

## Artifacts and publication

`release.yml` builds the signed AAB and the signed APKs in **two separate
Gradle invocations** (AAB first) because AGP 9 refuses an AAB together with
ABI-split APKs and resource shrinking ([issuetracker 402800800](https://issuetracker.google.com/402800800));
`app/build.gradle.kts` disables `splits.abi` only for `bundle*` invocations.
Every release must contain:

- `app-armeabi-v7a-release.apk`, `app-arm64-v8a-release.apk`,
  `app-x86-release.apk`, `app-x86_64-release.apk`,
  `app-universal-release.apk`,
- the `.aab`, and `SHA256SUMS.txt`.

Publication uses `gh release create ... --latest`, and a final step asserts that
the new tag is the repository's latest release and that every asset above is
attached. Runs are serialized (`concurrency: android-release`), and a
superseded pending run's commits are included in the next release's range.

Pull-request CI (`.github/workflows/build.yml`) exercises the same two release
Gradle invocations and checks all five APKs plus the AAB, so a broken release
path cannot be merged.

## خلاصهٔ فارسی

با هر merge روی `main` یک نسخهٔ تازه ساخته می‌شود، ولی خودِ اتوماسیون تصمیم
میگیرد نسخه چقدر جلو برود: معمولاً فقط یک patch؛ جهش minor فقط با شواهد کافی و
فاصلهٔ زمانی/تعداد نسخه، و جهش major فقط با اعلام صریح تغییر ناسازگار. بنابراین
شماره نسخهها بهآرامی پیش میروند. تمام ایجنتها موظفاند changelog را **فقط** همان
نسخه، با ایموجی، در همان GitHub Release بنویسند و چیزی از نسخههای قبل کپی
نکنند. هر نسخه APK امضاشده برای چهار معماری بهعلاوهٔ universal، فایل AAB،
checksum و برچسب `latest` دارد.
